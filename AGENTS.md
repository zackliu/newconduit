This repository is the design and future implementation workspace for **Agent Runtime Sidecar**, a runtime layer for running stateful, interactive agents as durable online services.

## Product Invariants

- A session is the durable identity. A worker is replaceable compute.
- Tenant is a high-level runtime boundary, not a small request field. Default to tenant-scoped ownership for runtime state and adapters; only tenant discovery, tenant creation, tenant registry, and cross-tenant operations belong to the outer central layer.
- Recovery starts from event logs and workspace snapshots. A unified semantic context format is a later validation item, not a V1 assumption.
- The central session service owns session catalog, worker registry, routing, connection state, authorization, and audit boundaries.
- Authorization must be enforced on session creation, connection, message routing, event replay, artifact access, and worker registration.
- The sidecar adapts existing agent processes first. The process-wrapper path is the preferred initial wedge.
- V1 should focus on homogeneous worker pools, self-hostable deployment, workspace-heavy long-running agents, and clear recovery semantics.
- Do not turn the product into a model provider, a full agent framework, a hosting platform, a marketplace, or a general application builder.

## Future Code Guidelines

- Do not start implementation from an unresolved design conversation. Confirm the design decision or implementation slice first, then edit code.
- Define stable runtime contracts before implementation: session catalog, worker registry, routed event model, sidecar protocol, storage adapter, and SDK surface.
- Keep central service, sidecar, persistent storage, and SDK/API concerns separated. Avoid leaking worker-local assumptions into public APIs.
- Before placing any class, controller, adapter, registry, or config, decide its ownership boundary first: outer central, tenant runtime, sidecar, or shared contract. If it reads/writes AgentSpec, Session, Worker, Event, WorkspaceSnapshot, Policy, Audit, transport config, storage, or hosting config for runtime execution, it is tenant-scoped by default and should be reached through `TenantRuntime` or a tenant-owned class.
- The outer central layer must not directly instantiate or call tenant-owned adapters/controllers such as WebPubSub transport, storage, AgentSpec registry, Worker registry, policy hooks, audit sinks, Docker hosting, or snapshot adapters. It should resolve/create tenants and delegate to tenant runtime instances.
- Prefer structured payloads, schemas, and typed event models over ad hoc strings.
- Use explicit named exports in barrel files. Do not use `export * from ...`; list concrete classes and types so public contracts stay reviewable.
- Keep model-visible context bounded. Any future prompt, context, memory, or event replay path needs explicit size limits and summarization behavior.
- Design for tenant isolation, auditability, and recovery from the first implementation slice.
- Avoid hidden special cases that encode a desired net effect directly. Model policy, subsidy, or override behavior as explicit mechanisms.
- Do not hardcode config-value strings in `src/` (AgentSpec/WorkerType/WorkerPool/host-pool class names, policy names such as `docker-workspace-volume-snapshot` or `stop-on-pause`, per-instance ids such as `docker-dotnet`, or per-pool env var names such as `DOTNET_WORKER_POOL_ID`). User-configurable desired-state lives in `config/` documents; each adapter, persistence class, and host-pool adapter self-declares a `classId`, and `src/` resolves config values through generic `registry.get(value)` lookups with no per-value branches.
- Do not write fallback code, compatibility shims, legacy compatibility layers, dual behavior paths, or "just in case" recovery branches unless the user explicitly asks for a migration or compatibility plan.
- When something fails, debug in this order: first ask whether the design/model is wrong, then whether the implementation violates the design, and only then whether an explicit domain validation branch is missing.
- Fix errors at the root cause. Do not add guard logic that merely hides an inconsistent state or papers over a broken contract.
- Tests must assert business behavior, runtime invariants, and public contract outcomes. Do not write tests that pass by asserting source-code shape, private helper structure, or implementation text unless the source shape is itself the generated business contract.

## Current Validation State

- TypeScript POC scaffold is present under `src/`.
- Demo AgentSpec, WorkerPool, and host-pool-controller definitions are declarative JSON documents under `config/` (`agent-specs/`, `worker-pools/`, `host-pool-controllers/`) and are the default startup config source (`CONFIG_DIR` defaults to `config`); the sidecar container ships them via `COPY config ./config`. Worker types are image-declared code build profiles in `src/sidecar/worker-types.ts` (they only name the adapter combination), not config. Matching is pure labels: an AgentSpec's `workerSelector.matchLabels` (including a conventional `storage` capability label) is matched against worker labels, there is no `sidecarClass`; worker labels + capacity are declared once on `WorkerPool.template`. The concrete storage driver is code — a worker reports its `storageClass` at registration and central records it — and snapshots/`workspaceRef` are opaque handle envelopes with no filesystem path or backend prefix. `src/` holds no hardcoded AgentSpec/WorkerPool definitions. A pool's optional `reuse` property (absent/`true` = shared; `false` = no-reuse) is a central-enforced placement policy: a no-reuse worker is bound to one session (`boundSessionId`, stamped at correlate and assignment) and the WorkerSelector never places another session on it, so a paused session resumes onto its own worker while it is alive; no-reuse pools scale one **session-pinned** host-pool instance per queued session (the instance carries `boundSessionId` + the session's stable `workspaceRef`), which lets a session-keyed durable host (a Foundry sandbox) stay stable across pause/resume.
- Customer-facing TypeScript SDK package is present under `sdk/client/`; SDK source is under `sdk/client/src/`, SDK tests are under `sdk/client/tests/`, and SDK public protocol source of truth is `sdk/client/public-protocol-spec-ch.md`.
- Scenario-based tests are under `tests/`; `pnpm test` compiles them to ignored `dist-tests/` output before running Node's test runner.
- Web PubSub integration tests read `tests/.env` for `WEBPUBSUB_ENDPOINT` and use `DefaultAzureCredential`; run `az login` before expecting those tests to exercise the real Azure service.
- Real Copilot SDK agent smoke tests read `tests/.env` for `RUN_REAL_COPILOT_AGENT_E2E`, `COPILOT_MODEL`, `COPILOT_PROVIDER_TYPE`, and `COPILOT_PROVIDER_BASE_URL`; provider auth uses Azure Identity/MSI, so run `az login` locally.
- The Docker hostPoolAdapter only `docker run`s a pre-built sidecar image; building the image is out of band (`pnpm build:sidecar-image`), not part of scale-out. `HostPoolController` config is `id + adapterKind + imageName + workerType` (no build inputs).
- The Foundry hostPoolAdapter (`FoundryHostPoolAdapter`, classId `foundry`) is a config-selected peer of the Docker adapter that runs the sidecar image on Azure AI Foundry hosted agents. Because a Foundry sandbox is host-managed durable storage (no snapshot capture), the Foundry session **is** our session's durable workspace: no-reuse pools scale one **session-pinned** instance per queued session (the instance carries `boundSessionId` + the session's stable `workspaceRef`), `scaleOut` first `POST /stop`s the session to normalize any prior state (not-exist / `idle` / stale-`active`) to no-live-compute, then opens one held `POST /invocations` liveness request per worker with `agent_session_id` = the instance's `workspaceRef` (boot payload carries centralUrl/tenantId/workerTypeId/labels/capacity/workerPool ids), returns `{containerId: sessionId}`, and reconnects with the same id on a drop; normalizing first guarantees a fresh container whose boot-once sidecar registers under this instance id (a still-warm container would keep the old sidecar under the previous instance id and never correlate — that was the pause/resume hang). `scaleIn` aborts the held request, then honors a `durableAction`: `retain` (bound session still alive, e.g. paused) `POST /stop`s the Foundry session to `idle` (compute released, sandbox + `$HOME` kept) so a resume — a fresh session-pinned instance carrying the same `workspaceRef` — re-invokes the stopped session into a fresh container generation with the workspace intact; `release` (bound session ended, or an unpinned/shared instance falling back to a per-instance `w-<instanceId>` id) `DELETE`s it. Foundry session status is `active` | `updating` | `idle` | `deleted`; aborting the liveness request alone leaves the container warm ~15 min, so the explicit stop is what makes the session cleanly reusable. Central derives `durableAction` from the bound session's liveness at scale-in (`WorkerPoolManager.resolveDurableAction`) and pre-binds the correlated worker to its pinned session so no other session is ever placed on it. The client controls the session id via the `agent_session_id` query parameter (the `x-agent-session-id` header is platform→container injection and is ignored if a client sends it). Commands still flow over Web PubSub. Its config lives in the default `config/` profile alongside the Docker pools (the `foundry` host-pool-controller, `foundry-copilot` pool, and `copilot-foundry` AgentSpec), so one central serves Docker and Foundry pools together, routed by the `storage` capability label; the Foundry controller declares its own `centralUrlForWorkers` (a Foundry cloud worker reaches central over a public URL, resolved per host-pool-controller with the global `CENTRAL_URL_FOR_WORKERS` as fallback default), and the image variant is `containers/sidecar-foundry/Dockerfile` (`ENV SIDECAR_HOST_CLASS=foundry`), and deploy is bring-your-own-image via `azd ai agent init --image ... --protocol invocations`; see `foundry/README.md`. The Foundry worker uses worker-type `copilot-local` (storage class `host-managed`) because a Foundry sandbox has no Docker volumes.
- Docker WorkerPool e2e tests require Docker Desktop, local `az login`, and `RUN_DOCKER_WORKERPOOL_E2E=1`; they build the sidecar image in test setup (`containers/sidecar/Dockerfile`), mount the host Azure CLI profile, start a Docker sidecar through WorkerPool scale-out, and validate scale-in. Two scenarios run on `reuse: false` pools: (1) scale-out → turn → pause → scale-in; (2) memory restore across worker recycle — a real Copilot agent uses its tools to write a file (the test runs a client `session.observe()` loop that approves the tool `interaction.requested` prompts), the workspace is snapshotted, the worker recycles, and a fresh worker restores the workspace and reads the file back.
- Foundry WorkerPool e2e (`tests/workerpool/foundry-workerpool.integration.test.ts`) is gated off unless `RUN_FOUNDRY_WORKERPOOL_E2E=1` with `FOUNDRY_PROJECT_ENDPOINT` + `FOUNDRY_AGENT_NAME` (from `tests/.env`) and `az login`; it drives the full boot → pause → resume → release cycle on a pinned `workspaceRef`: boot leaves the session `active`, a `retain` scaleIn (pause) stops it to `idle` (reusable, not deleted), a fresh instance re-invokes the same `workspaceRef` back to `active`, and a `release` scaleIn (session end) deletes it. The Foundry adapter unit tests and config test run in the normal `pnpm test` (no Azure needed).
